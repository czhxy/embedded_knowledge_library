# 嵌入式内存布局

## 链接脚本（Linker Script）
> 链接脚本（.ld 文件）是嵌入式开发中最重要但最容易被忽略的文件之一。它告诉链接器如何将各个目标文件（.o）中的段（section）映射到最终的可执行文件中，决定了程序在内存中的布局。
>
> 面试常问：
> • LMA 和 VMA 有什么区别？
> • .data 段为什么需要 LMA ≠ VMA？
> • 链接脚本导出了哪些关键符号？启动代码如何使用它们？
- **定义每个段的 VMA（运行地址）和 LMA（加载地址）**
  > VMA（Virtual Memory Address / 运行地址）：程序运行时，CPU 从该地址读取指令或数据。所有代码段和 RAM 中的可读写段都需要 VMA。
  >
  > LMA（Load Memory Address / 加载地址）：程序在烧录/下载时存放的位置。通常指向 Flash。
  >
  > 典型例子（STM32）：
  >   .text   → VMA=0x08000000, LMA=0x08000000（代码直接从 Flash 运行）
  >   .data   → VMA=0x20000000, LMA=0x0800xxxx（初始值在 Flash，启动时拷贝到 RAM）
  >   .bss    → VMA=0x2000xxxx, 无 LMA（只需要在 RAM 中预留空间并清零）
- 各段 LMA/VMA 关系：.text/.rodata (LMA=VMA) | .data (LMA≠VMA) | .bss (仅 VMA)
  > 三段三态：
  >
  > 1. .text 和 .rodata —— 只读，LMA = VMA
  >    CPU 直接从 Flash 取指令/读常量，不需要搬运。
  >
  > 2. .data —— 可读写，LMA ≠ VMA
  >    LMA 指向 Flash（存初始值），VMA 指向 RAM（运行地址）。启动代码必须从 LMA 搬运到 VMA。
  >
  > 3. .bss —— 零初始化，只有 VMA
  >    不需要 LMA，因为所有初始值都是 0。启动代码只需要把对应 RAM 区域清零。
  >
  > 这是为什么启动代码（startup）必须做的事情就是：搬 .data，清 .bss，然后才跳转到 main()。
- 导出关键符号：_sdata/_edata, __bss_start__/__bss_end__, _estack
  > 链接脚本中定义的符号没有“值”——它们只是地址标记，供启动代码引用：
  >
  > • _sdata / _edata：.data 段在 RAM 中的起止地址
  > • _sidata（或 _etext）：.data 段在 Flash 中的初始值起止
  > • __bss_start__ / __bss_end__：.bss 段在 RAM 中的起止
  > • _estack：栈顶地址（通常是 RAM 末尾 + 1）
  >
  > 验证方法：
  >   arm-none-eabi-nm firmware.elf | grep -E "_sdata|_edata|__bss|_estack"
  >   arm-none-eabi-objdump -t firmware.elf
  >
  > 常见面试陷阱：
  >   问“链接脚本导出的符号是什么类型？”——不是变量，只是地址标记，不能对其赋值，只能取其地址（&）。
- 设置堆栈大小（_Min_Heap_Size, _Min_Stack_Size）
  > 在链接脚本中通过 ASSERT 和 PROVIDE 语句预留堆栈空间：
  >
  >   _Min_Heap_Size = 0x200；  /* 512 字节 */
  >   _Min_Stack_Size = 0x400； /* 1024 字节 */
  >
  > 这些值决定了 .heap 和 .stack 段的最小大小。如果实际使用超出此值，不会报错——因为只是“最小保证”，超出部分会覆盖相邻区域，导致堆栈冲突。
  >
  > 对于裸机程序：只有 MSP（主栈），_estack 指向栈顶。
  > 对于 RTOS：每个任务有自己的任务栈，_Min_Stack_Size 主要给中断栈（MSP）用。
## 两个主要位置
- **flash**
  - **中断向量表（Vector Table）**
    > 中断向量表位于 Flash 的起始位置（STM32 默认 0x08000000），是 Cortex-M 启动流程的第一站。
    >
    > 重要知识点：
    > • 向量表位置可通过 SCB->VTOR 寄存器重映射到 RAM（用于 IAP/OTA）
    > • 启动时硬件自动读取前两项，无需任何代码执行
    > • 向量表缺失或错误 → HardFault（最难调试的 bug 之一）
    - **第 0 项：MSP 初始值**
      > 向量表第 0 项（地址 0x00000000/0x08000000）存储的是主栈指针（MSP）的初始值，不是代码地址。
      >
      > 硬件行为：上电后，CPU 自动从向量表第 0 项加载 MSP，然后从第 1 项取复位向量并跳转。
      >
      > 典型值：RAM 起始地址 + RAM 大小，如 STM32F407 为 0x20020000（128KB RAM）。
      >
      > 这也能解释为什么栈从高地址向低地址生长——MSP 初始值通常是 RAM 的最后一个地址。
    - **第 1 项：Reset_Handler 入口地址**
      > 向量表第 1 项（地址 0x00000004）存储 Reset_Handler 的函数地址。
      >
      > 启动流程：
      > 1. 硬件从第 0 项加载 MSP
      > 2. 硬件从第 1 项读取 Reset_Handler 地址
      > 3. CPU 跳转到 Reset_Handler（通常是一段汇编代码）
      > 4. Reset_Handler 中执行：搬 .data、清 .bss、调 SystemInit()、调 main()
      >
      > 面试常问：为什么第 1 项的最低 bit 必须是 1？——因为 Cortex-M 使用 Thumb 指令集，地址的 bit[0] 必须为 1 表示 Thumb 状态，否则进入 HardFault。
    - 后续：NMI / HardFault / SysTick / 外设中断地址
      > 中断向量表的标准布局（Cortex-M）：
      >
      > 异常（系统级）：
      > • -14: NMI（不可屏蔽中断）
      > • -13: HardFault（硬件错误）
      > • -12: MemManage（MPU 违例）
      > • -11: BusFault（总线错误）
      > • -10: UsageFault（未定义指令等）
      > • -5: SVCall（SVC 指令）
      > • -2: PendSV（OS 上下文切换用）
      > • -1: SysTick（系统定时器，RTOS 心跳）
      >
      > 外设中断（从 0 开始）：
      > • 0~N：WWDG、PVD、TIM、USART、SPI 等
      >
      > 每个中断序号对应 4 字节的 ISR 函数地址。向量表的总大小 = 16（系统异常）+ 外设中断数。
    - **未填写 ISR → HardFault**
      > 如果中断被使能但对应的向量表项填写的是默认的 Default_Handler（通常是一个死循环），程序会卡死但不会触发 HardFault。
      >
      > 但如果向量表项是 0x00000000（未初始化），当中断发生时 CPU 会尝试跳转到地址 0x00000000 = MSP 初始值，这几乎必然导致 HardFault。
      >
      > 调试技巧：
      > 1. 在 HardFault_Handler 中打断点，查看 SP 指向的栈帧
      > 2. 通过栈帧中的 PC 值反推是哪个中断没注册
      > 3. 打印 SCB->HFSR / CFSR / MMFAR / BFAR 寄存器辅助排查
      >
      > 常见原因：忘记在启动文件中添加中断服务函数名。
  - **存储的内容包括：**
    1.代码（CODE或.text）
    2.常量，字符串字面量（RO-DATA或.rodata）
    3.有初始值且不为0的静态/全局变量（RW-DATA或.data）注意：这里存的是镜像值，实际运行的时候是会拷贝到ram中的
    > Flash 是嵌入式系统中存储固件的非易失性存储器。
    >
    > 三个主要内容：
    > 1. .text（代码段）：编译后的机器指令，CPU 直接从这里取指令执行（XIP - Execute In Place）
    > 2. .rodata（只读数据）：const 全局变量、字符串字面量（如 printf 的格式串）
    > 3. .data 的初始化镜像：有初值的全局/静态变量的初始值存放在 Flash 中，启动时由启动代码拷贝到 RAM
    >
    > 为什么 .data 要在 Flash 存一份？因为 RAM 是易失性的，断电后数据丢失。初始值必须固化在 Flash 中，每次上电后再复制到 RAM。
- **ram**
  - **内存段包括：**
    1.RW-DATA或.data(有初始值且不为0的静态/全局变量真正运行的地方)
    2.ZI-DATA或.bss（无初始值或有初始值但为0的静态/全局变量运行的地方）
    3.heap（malloc分配数据的地方）
    4.stack
    - **1.RW-DATA**
      - **初始化在flash中，运行时拷贝副本到ram中**
        > .data 段在 RAM 中分配空间，但初始值（非零值）保存在 Flash 中。启动时由 Reset_Handler 将 Flash 中的初始值复制到 RAM。
        >
        > 这就是 .data 段的 LMA ≠ VMA 的实际体现：
        > • LMA = Flash 地址（存放初始值）
        > • VMA = RAM 地址（运行时使用）
        - **拷贝时机：**
          1. 初始化栈指针（MSP）（硬件自动从向量表第0项加载）
          2. 进入reset_handler
          3.从 Flash 的 .data 初值镜像区拷贝到 RAM 的 .data 运行区,并将 RAM 中 .bss 段清零
          4. 调用 SystemInit()（时钟配置）
          5. 跳转到 main()
          > 这是 Cortex-M 上电后的标准启动序列，对应 startup 汇编文件中的 Reset_Handler 函数。
          >
          > 第 3 步是关键——搬移 .data 和清零 .bss 是 main() 运行环境的准备。如果这一步没做好，全局变量的初始值就是随机的脏数据，导致难以调试的 bug。
          >
          > ARMCC/ARMClang 使用 __main（注意不是 C 的 main），GCC 使用 _start → Reset_Handler 的调用链。不同编译器的实现略有差异，但本质逻辑相同。
    - **2.ZI-DATA**
      > .bss 段（Block Started by Symbol）存放未初始化和初始化为 0 的全局/静态变量。在可执行文件中不占实际空间（只记录大小），运行时在 RAM 中分配并清零。
      - 初始化被清零。清零时依赖链接符号（如 __bss_start__、__bss_end__），这些符号在链接脚本中定义，启动代码根据符号来清零 RAM中的 .bss 区域
        > .bss 清零的汇编伪代码：
        >
        >   ldr r0, =__bss_start__
        >   ldr r1, =__bss_end__
        >   movs r2, #0
        >   bss_loop:
        >     cmp r0, r1
        >     bge bss_done
        >     str r2, [r0]
        >     adds r0, #4
        >     b bss_loop
        >   bss_done:
        >
        > 之所以能在 main() 前把 .bss 清零，是因为链接脚本导出了 __bss_start__ 和 __bss_end__ 符号，startup 汇编代码直接引用这些符号的地址。
        >
        > 注意：C 标准规定未初始化的静态变量默认值为 0——这正是通过 .bss 清零机制保证的。
    - **3.heap（堆）**
      > 堆用于动态内存分配（malloc/calloc/realloc/free）。在嵌入式系统中，堆的使用需要格外谨慎：
      >
      > • 碎片化风险：频繁的 malloc/free 导致堆碎片化，最终可能分配失败
      > • 实时性不确定：malloc 的执行时间不定
      > • 堆与栈相邻且相向增长，可能发生碰撞
      >
      > MISRA C 甚至禁止在安全关键系统中使用动态内存分配。
      - **堆栈碰撞（Stack-Heap Collision）**
        > 堆和栈共享同一块 RAM，但增长方向相反：
        >
        > • 堆：从低地址向高地址增长（malloc 时 _sbrk 增大）
        > • 栈：从高地址向低地址增长（函数调用时 SP 减小）
        >
        > 当两者“相遇”时发生碰撞，导致：
        > • 栈覆盖堆分配的数据 → 数据损坏
        > • 堆覆盖栈帧 → 函数返回地址被修改 → 程序跑飞
        >
        > 防范方法：
        > 1. 增大 _Min_Heap_Size 和 _Min_Stack_Size（链接脚本）
        > 2. 在 HardFault_Handler 中检查栈溢出标志
        > 3. 使用 MPU 设置栈保护区域（Guard Region）
        > 4. RTOS 中使用 uxTaskGetStackHighWaterMark() 监控任务栈使用量
        >
        > 面试考察点：能说清碰撞机制、危害和防范措施，表明有实际调试经验。
    - **4.栈（stack）相关:**
      > 栈是函数调用的核心支撑机制。Cortex-M 的栈是满递减栈（Full Descending）——SP 始终指向最后一个入栈的数据，入栈时 SP 先递减再存储。
      - (1)函数不会自己新建一个栈区。栈是系统/启动代码预先分配好的一块连续内存区域，函数被调用时只是在这块已有的栈上移动栈指针（SP），划出一段叫栈帧（Stack Frame）的区域来存放局部变量——这不是新建栈，而是在同一块栈里“切片”。
        > 理解这一点很重要——很多初学者误以为“每个函数都有自己的栈”。实际上：
        >
        > • 只有一个栈区域（或 RTOS 中每个任务一个任务栈）
        > • 函数调用时，SP 向下移动，划出一段空间（栈帧）
        > • 函数返回时，SP 向上恢复，释放该栈帧
        >
        > 这就是为什么局部变量的“生命周期”与函数调用绑定——栈帧释放后，那块内存可能随时被下一个函数调用覆盖。返回局部变量的地址（指针）是未定义行为。
      - (2)裸机/单线程：只有一条主栈 MSP，所有函数（包括中断）的局部数组都在 MSP 上，靠 SP 切片。
        RTOS（FreeRTOS 等）：每个任务有独立的 任务栈 PSP，任务里调用的函数局部数组落在该任务的 PSP 上；中断仍用 MSP。
        > Cortex-M 双栈机制：
        >
        > • MSP（Main Stack Pointer）：上电默认使用，中断和裸机程序的主栈。复位后 R13=MSP。
        > • PSP（Process Stack Pointer）：RTOS 任务栈，需要通过 CONTROL 寄存器切换。
        >
        > RTOS 的实际运行模式：
        > 1. 中断/异常上下文 → 自动使用 MSP
        > 2. 任务上下文 → 使用 PSP（通过 CONTROL[1]=1 切换）
        > 3. 上下文切换时，RTOS 保存/恢复每个任务的 PSP 值
        >
        > 这是 FreeRTOS 等 RTOS 能实现任务栈隔离的硬件基础。每个任务看起来“独占”一段栈，互不影响。
      - **（3）局部变量存储在栈中，每次进入时随机脏值，函数返回后失效**
        > 局部变量（不加 static 修饰）在栈帧中分配：
        >
        > • 分配方式：SP 向下移动 sizeof(var) 个字节
        > • 初始值：不确定（脏值），因为栈上那块内存可能被之前的函数调用写过
        > • 生命周期：函数返回后，栈帧释放，该内存不再有效
        >
        > 因此：
        > • 必须在使用前初始化局部变量
        > • 不能返回局部变量的地址（悬垂指针）
        > • 对于大数组（>KB 级别），要小心栈溢出——考虑用 static 或 malloc 代替
## const 变量的存储位置
> const 关键字在 C 语言中表示“只读”，但变量的实际存储位置取决于它的作用域和存储类别。很多人以为 const 变量一定在 Flash 中——这是一个常见的理解误区。
>
> 面试考察点：
> • const 全局变量和 const 局部变量存储位置一样吗？
> • 为什么 const 局部变量在栈上？
> • const 变量可以通过指针修改吗？有何后果？
- const 全局/静态变量 → .rodata（Flash 中，只读）
  > 在文件作用域定义的 const 变量（包括 static const）存储在 .rodata 段，位于 Flash 中。
  >
  > 示例：
  >   const int MAX_SIZE = 100;       // → .rodata（Flash）
  >   static const char* NAME = "X"; // → .rodata（Flash）
  >
  > 验证方法：
  >   arm-none-eabi-objdump -h firmware.elf | grep rodata
  >   arm-none-eabi-readelf -S firmware.elf | grep rodata
  >
  > 注意事项：
  > • .rodata 中的内容不可被程序修改，写保护
  > • 字符串字面量也存储在 .rodata 中
  > • 不同编译器的放置策略可能略有差异，但 const 全局变量进 .rodata 是通用规则
- **const 局部变量 → stack（栈上，非 Flash）**
  > const 局部变量（函数内部定义的 const 变量）存储在栈上，而不是 Flash。
  >
  > 示例：
  >   void func(void) {
  >     const int x = 10;  // → 栈上分配，与普通局部变量一样
  >   }
  >
  > 原因：局部变量具有自动存储期，必须在栈帧中分配和释放。const 只约束“不可修改”，不影响存储期。
  >
  > 这意味着：
  > • const 局部变量每次函数调用都会重新在栈上分配
  > • 它的初始值 10 在函数返回后就不存在了
  > • 只有在函数执行期间，才受 const 保护（编译器层面，非硬件保护）
  >
  > 这是面试中的经典陷阱题——能从 const 的作用域+存储期两个维度区分回答，表明理解深刻。
## static 关键字的存储位置影响
> static 关键字在 C 语言中有三个主要用途，分别影响变量的生命周期、作用域和函数的可见性。static 改变了符号的链接属性，但不改变段的归属规则。
>
> 面试考察点：
> • static 局部变量和全局变量存储在哪？生命周期有什么区别？
> • static 函数与普通函数在内存布局上有区别吗？
> • 为什么嵌入式开发中推荐多用 static？
- static 全局变量 → .data/.bss（作用域限本文件）
  > static 修饰的全局变量仍然存储在 .data（有初值）或 .bss（零/无初值），只是作用域被限制在当前编译单元（.c 文件）。
  >
  > 示例：
  >   static int g_count = 0;   // → .bss，但符号不导出
  >   static int g_flag = 1;    // → .data，但符号不导出
  >
  > 存储位置不变的原因：static 只影响符号的链接属性（从全局可见变为文件内部可见），不影响变量的存储类别。
  >
  > 好处：
  > • 防止命名冲突：多个 .c 文件可以定义同名 static 变量
  > • 信息隐藏：其他文件无法 extern 引用
  > • 有利于编译器优化（内联、常量传播等）
- static 局部变量 → .data/.bss（生命周期=整个程序）
  > static 局部变量虽然定义在函数内部，但存储在 .data 或 .bss 段（而非栈上），生命周期为整个程序运行期。
  >
  > 示例：
  >   void counter(void) {
  >     static int count = 0;  // → .bss，不是栈
  >     count++;
  >   }
  >
  > 关键区别：
  > • 普通局部变量 → 栈上分配，函数返回即失效
  > • static 局部变量 → .data/.bss，程序运行期间一直存在
  > • static 局部变量只初始化一次（第一次进入函数时），之后保持值
  >
  > 典型用途：
  > • 函数调用计数器
  > • 缓存上一次计算结果
  > • 状态机中的状态变量
  >
  > 验证方法：观察 map 文件中 .data/.bss 段的大小是否包含了 static 局部变量。
- **static 函数 → 符号不导出（仍在 .text）**
  > static 函数与普通函数一样存储在 .text（代码段），唯一的区别是编译后的符号不导出到符号表，其他 .c 文件无法链接到它。
  >
  > 示例：
  >   static void helper(void) { ... }  // → .text，但符号不可被外部引用
  >
  > 实际影响：
  > • 函数体仍在 Flash 的 .text 段
  > • 没有运行时开销（不像 C++ 的 virtual）
  > • 编译器可以更激进地优化（内联、去掉未调用的 static 函数）
  > • 防止链接时符号冲突
  >
  > 嵌入式开发建议：
  >   MISRA C 建议将不对外暴露的函数声明为 static，既安全又有利于优化。
  >   特别是中断服务函数调用的小工具函数，声明为 static 可以避免被意外调用。
