## lwIP
- lwIP 是嵌入式领域的“精简版 TCP/IP 协议栈”，适合在 MCU 上实现联网，核心是 pbuf、netif、可裁剪配置以及 Raw/Netconn/Socket 三类 API
## TCP/IP
- **一、为什么需要协议栈**
  - **场景：STM32 通过网口把温度数据发给电脑**
  - 要解决的问题：这串 0/1 是什么？多设备同时发会不会冲突？传错怎么办？经路由器怎么找到目标设备？
  - 本质：协议栈是一套约定规则，让不同设备/系统可靠有序交换数据；TCP/IP 是最通用的一套，把复杂通信拆成多层
- **二、TCP/IP 四层模型（嵌入式视角）**
  - **1. 网络接口层（链路层）**
    - **作用：同一物理网络内传输数据帧，处理 MAC 地址、冲突检测**
    - **典型协议/硬件：Ethernet、Wi-Fi、ARP**
    - **嵌入式对应：网卡驱动、PHY、MAC 控制器**
  - **2. 网络层**
    - **作用：跨网络寻址和路由，把数据包从源主机送到目的主机**
    - **典型协议：IP、ICMP**
    - **嵌入式对应：IP 路由表、分包重组**
  - **3. 传输层**
    - **作用：端到端通信服务（可靠/不可靠），区分不同应用**
    - **典型协议：TCP、UDP**
    - **嵌入式对应：连接管理、重传、流量控制**
  - **4. 应用层**
    - **作用：定义数据格式和语义**
    - **典型协议：HTTP、MQTT、Modbus TCP**
    - **嵌入式对应：业务逻辑代码**
- **三、各层关键概念（重点掌握）**
  - **网络接口层：以太网和 MAC 地址**
    - MAC 地址：48位，烧录网卡硬件，全球唯一；同一局域网内通过 MAC 直接通信
    - 以太网帧格式：目标MAC(6字节)+源MAC(6字节)+类型(2字节)+数据(46~1500字节)+CRC(4字节)
    - ARP：知道 IP 不知 MAC 时广播询问；ARP 表缓存结果
    - 嵌入式注意：MCU 集成 MAC 但需外接 PHY（LAN8720/DP83848）；驱动处理 DMA 描述符、中断
  - **网络层：IP 协议**
    - IP 地址：32位(IPv4)，网络号+主机号（子网掩码划分）
    - IP 包格式：版本/首部长度/总长度/TTL/协议(6=TCP,17=UDP)/源IP/目标IP/数据
    - **路由：目标不在本网段→发默认网关，路由器逐跳转发**
    - 分片重组：超 MTU(1500) 分片；嵌入式内存小，尽量避开分片（设 TCP MSS 或 UDP 小包）
    - 嵌入式注意：lwIP 默认不支持分片重组（耗 RAM），需配置开启
  - **传输层：TCP 和 UDP**
    - **UDP（用户数据报协议）**
      - **特性：无连接、不可靠、不排序、不保证送达**
      - **头部：8字节（源端口/目标端口/长度/校验和）**
      - 适用：实时性高、允许少量丢包——视频流、在线游戏、DNS、传感器周期上报
      - **嵌入式优点：实现简单、内存占用极小、无连接开销**
    - **TCP（传输控制协议）**
      - 特性：面向连接、可靠、字节流；靠序号/确认/重传/流量/拥塞控制保证正确有序
      - 头部：至少20字节（端口/序号/确认号/标志位SYN·ACK·FIN·RST/窗口/校验和）
      - 适用：要求数据完整性——网页、文件传输、MQTT(可选用TCP)
      - 嵌入式注意：状态机复杂，需较多 RAM 保存连接状态、收发缓冲区
- **四、TCP 三次握手与四次挥手（面试高频）**
  - **三次握手（建立连接）**
    - ① 客户端→服务器：SYN(SYN=1,seq=x)，进入 SYN_SENT
    - ② 服务器→客户端：SYN+ACK(SYN=1,ACK=1,seq=y,ack=x+1)，进入 SYN_RCVD
    - ③ 客户端→服务器：ACK(ACK=1,seq=x+1,ack=y+1)，双方进入 ESTABLISHED
    - 为什么三次：防止失效连接请求导致服务器误建连接；同时确认双方收发能力正常
  - **四次挥手（断开连接）**
    - ① 主动方→被动方：FIN(seq=u)，进入 FIN_WAIT_1
    - ② 被动方→主动方：ACK(ack=u+1)，进入 CLOSE_WAIT；主动方进入 FIN_WAIT_2
    - ③ 被动方→主动方：FIN(seq=v)，进入 LAST_ACK
    - ④ 主动方→被动方：ACK(ack=v+1)，进入 TIME_WAIT 等 2MSL 后关闭
    - 为什么四次：全双工每方向单独关闭；被动方可能还有数据，先 ACK 再发 FIN
  - TIME_WAIT 作用：确保最后 ACK 到达（丢则对方重发 FIN）；让旧连接数据包消失避免影响新连接
  - **嵌入式注意**
    - **多并发连接：每连接维护状态，RAM 消耗大**
    - SYN Flood：大量 SYN 不完成握手占满连接表→设最大连接数、超时时间
    - lwIP：可配置 MEMP_NUM_TCP_PCB 等限制连接数量
- **五、TCP 可靠传输核心机制**
  - 序号与确认：每字节编号，确认连续字节（收 seq=100 长200 → 回 ack=300）
  - 超时重传：定时器未收 ACK 则重传；RTT 动态估算超时时间 RTO
  - 滑动窗口：接收方告知可接收字节数（窗口），发送方据此控速避免溢出。还有mss制约，控制每个tcp块发送的数据大小，所以发送窗口可以分成两个部分，一个是已发送+为确认的，一个是可用窗口（可发送但还为发送的）。
  - **流量控制：通过窗口字段实现，防止发送太快淹没慢速接收方**
  - 拥塞控制：维护拥塞窗口 cwnd，慢启动/拥塞避免/快重传/快恢复（Tahoe、Reno）
  - 嵌入式注意：需定时器/缓冲区/内存管理；几十 KB RAM 可选 UDP 或简化 TCP（lwIP 裁剪）
- **六、粘包 与 半包**
  - **粘包**
    ​接收方一次读取，读到了多个完整的应用层消息。
    ​例如发送方分两次发送：
    ​send("hello")
    ​send("world")
    ​接收方可能一次收到："helloworld"
  - **半包/拆包**
      一个完整的应用层消息，被接收方拆成多次才读完。
    ​例如发送方发送：
    ​send("hello world")
    ​接收方先收到：
    ​"hel"
    ​再收到：
    ​"lo world"
  - **为什么会出现？**
     因为 TCP 是面向字节流的协议，它只保证字节顺序和可靠性，不保留你调用 `send/write` 时的消息边界。
     常见原因：
      - 发送方用了 Nagle 算法，把小包合并发送；
      - 接收方读取不及时，多个消息堆在缓冲区；
      - 数据超过 MSS/MTU，被 TCP 或 IP 分片；
      - 接收缓冲区大小限制；
      - 网络延迟、拥塞、滑动窗口变化等。
      所以：
      - 发送方一次 `send`，接收方不一定一次 `recv` 完；
      - 发送方多次 `send`，接收方也可能一次 `recv` 到。
    - 怎么解决
      核心思路：**在应用层自己定义消息边界**，接收端维护缓冲区，循环拆包。
      常用方案：
      1. 固定长度：每个消息长度固定。
      2. 分隔符：如 `\n`、`\r\n`、特殊字符。
      3. 长度字段：最常见，例如：
      [4字节消息长度][消息体]
     接收端先读长度，再读对应长度的消息体。
      4. TLV / 自定义协议：如 `[魔数][版本][长度][类型][数据]`
