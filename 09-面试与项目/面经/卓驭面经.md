## 卓驭
- 1. I2C 读寄存器时，主机发完地址后为什么要再发一次读位？NACK 出现在哪些环节？
  - 核心机制：I2C 是半双工总线，无独立方向线，方向全靠地址字节末位 R/W 位表达。
    读寄存器时序：Start→设备地址+W=0→寄存器地址→Repeated Start→设备地址+R=1→数据→Stop
  - 为什么再发一次读位：要切换成"从机→主机"方向，必须用 Repeated START 再发一次地址并把末位改成 R=1，从机才明白"轮到我发数据"；若只发一次（W=0），从机会一直认为你在写
  - **NACK 出现环节：**
    ① 寻址阶段：设备不存在/未上电/地址写错 → 无从机拉低 SDA
    ② 寄存器地址无效：从机不认识偏移，不回 ACK
    ③ 主机主动发 NACK（正常结束）：读最后一个字节时主机发 NACK 表示不要了
    ④ 总线异常：SDA 拉死/时钟拉伸超时/从机忙
  - 代码示例（write_byte/read_byte 返回值表示 ACK/NACK）：
        send_start();                        // 起始条件
        write_byte((dev_addr << 1) | 0x00);  // 设备地址 + W=0（等待从机应答 ACK）
        write_byte(reg_offset);              // 发送寄存器偏移地址（等待从机应答 ACK）
        send_repeated_start();               // 重复起始条件，切换方向
        write_byte((dev_addr << 1) | 0x01);  // 设备地址 + R=1（等待从机应答 ACK）
        data = read_byte(NACK);              // 读最后1字节，主机发 NACK 表示结束
        send_stop();                         // 停止条件
    应答责任方：地址/寄存器字节由"从机"应答；读数据阶段由"主机"应答（ACK=继续读，NACK=结束）
- 2. SPI 模式 0 和模式 3 在 CPOL、CPHA 上差在哪？从机采样边沿怎么选？
  - **CPOL/CPHA 含义：**
    CPOL 决定空闲电平：0=空闲低，1=空闲高
    CPHA 决定采样边沿：0=第1边沿采样，1=第2边沿采样
  - **四模式对照：**
    模式0：CPOL=0 CPHA=0 → 空闲低，第1边沿(上升沿)采样，第2边沿输出
    模式1：CPOL=0 CPHA=1 → 空闲低，第2边沿(下降沿)采样，第1边沿输出
    模式2：CPOL=1 CPHA=0 → 空闲高，第1边沿(下降沿)采样，第2边沿输出
    模式3：CPOL=1 CPHA=1 → 空闲高，第2边沿(上升沿)采样，第1边沿输出
  - 模式0与模式3差异：两者采样边沿都是上升沿，真正差在 CPOL（空闲电平）不同，由此决定"上升沿是第几个边沿"
  - 采样边沿选择：接收方必须在数据已稳定的边沿采样，不能与输出（数据翻转）同一边沿，否则误采；以从机芯片数据手册 CPOL/CPHA 为准；CPHA=1 通常让数据先建立再采样更稳妥
  - 记忆技巧：空闲电平决定第1边沿方向（空闲低→上升沿，空闲高→下降沿）；CPHA=1 在数据稳定后采样
- 3. DMA 搬运 ADC 采样结果到内存，还需要开 ADC 中断吗？半传输/全传输怎么用？
  - 还需要开 ADC 中断吗：仅搬数据用 DMA 的传输完成中断（TC）即可，不必开 ADC 的 EOC 中断；需要逐点实时响应（阈值判断/计数）时才开 ADC 中断
  - **半传输/全传输（乒乓缓冲）：**
    ADC 连续采样 + DMA 循环模式，HT=前半段搬满处理前一半，TC=后半段搬满处理后一半
    采集与处理构成流水线：前一半处理时 DMA 往后一半搬，交替进行互不丢数据
    前提：处理速度须快于 DMA 搬半段的时间
  - 为什么拆半/全：若等全部搬完才处理，处理耗时内 DMA 循环会覆盖新数据导致丢数据
  - **代码示例：**
    void DMA1_Channel1_IRQHandler(void) {
        if (DMA_GetITStatus(DMA1_IT_HT1)) {
            DMA_ClearITPendingBit(DMA1_IT_HT1);
            ProcessSamples(&adc_buf[0], BUF_SIZE/2);   // 处理前半
        }
        if (DMA_GetITStatus(DMA1_IT_TC1)) {
            DMA_ClearITPendingBit(DMA1_IT_TC1);
            ProcessSamples(&adc_buf[BUF_SIZE/2], BUF_SIZE/2); // 处理后半
        }
    }
- 4. Cortex-M 里 NVIC 抢占优先级和子优先级怎么配？同一抢占级能嵌套吗？
  - 分组配置：AIRCR 的 PRIGROUP 划分"抢占/子优先级"位宽
    STM32 分组：Group0=0抢占+4子优先，Group1=1+3，Group2=2+2，Group3=3+1，Group4=4+0
  - **配置代码：**
    NVIC_PriorityGroupConfig(NVIC_PriorityGroup_2);  // 2位抢占+2位子优先
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 1; // 抢占优先级
    NVIC_InitStructure.NVIC_IRQChannelSubPriority = 0;        // 子优先级
    NVIC_Init(&NVIC_InitStructure);
  - 同一抢占级能嵌套吗：不能。只有抢占优先级数值更小（更高）的中断才能打断嵌套；同抢占级只能按子优先级排队，子优先级不产生嵌套
  - 关键辨析：抢占优先级管"打断"，子优先级管"排队"；子优先级只在抢占相同时才起作用；Cortex-M 数值越小优先级越高
- 5. volatile 能保证多线程安全吗？和 atomic、关中断分别用在什么场景？
  - **本质区分（三者解决不同问题，组合而非互斥）：**
    volatile=解决"编译器缓存"（防止优化器缓存到寄存器，强制每次访问内存）
    atomic=解决"单变量读-改-写原子性"（保证 x++ 不可分割）
    关中断=解决"一段代码的临界区"（保证整段操作不被并发打断）
  - **volatile 详细场景**
    - **ISR 与主循环共享标志位（最经典）：**
      volatile uint8_t g_rx_done = 0;
      void USART1_IRQHandler(void) { g_rx_done = 1; }
      int main(){ while(1){ if(g_rx_done){...} } }
      为什么必须volatile：无它则编译器把变量缓存进寄存器，主循环if永远读旧值(0)，ISR改了内存也没用→死循环
    - 为什么编译器把变量缓存进寄存器、if 永远读旧值(0)——原理详解
      - 一句话结论：编译器不知道"中断会改这个变量"，它把循环里 if(flag) 只读了一次内存、存进寄存器，之后循环全用寄存器旧值(0)；ISR 改的是内存、循环读的是寄存器 → 永远对不上
      - **C 抽象机模型：**
        C 标准按"抽象机"定义行为，编译器可做任意优化，只要可观察行为不变（volatile访问/I/O/终止行为）
        抽象机认为变量只在"源码里写它的地方"才会变；主循环可见路径里 flag 没有任何写操作 → 编译器认为值不变
        中断对编译器不可见——不在抽象机的程序流里，编译器不会自动假设"有异步的东西会改 flag"
      - **三种优化叠加：**
        ① 循环不变代码外提：循环内无修改flag语句→视为循环不变量→把"读flag"指令从循环体提升到循环外，只读一次
        ② 寄存器分配：把读到的值放进寄存器，比较直接对寄存器操作，省掉每次内存访问
        ③ 常量传播/冗余加载消除：既然值不变，循环里重复读合并成一次
      - **汇编证据（非volatile，-O2）：**
            ldr  r2, =flag
            ldrb r0, [r2]    // ★循环外只读一次内存 → r0=0
        .L2: cbz r0, .L2     // ★之后永远用寄存器r0判断，循环内不再碰内存
        ISR 改了内存 flag=1，循环用 r0 还是 0 → if 永远为假，甚至可能优化成空死循环
      - **汇编证据（加volatile，-O2）：**
        .L2: ldrb r0, [r2]   // ★每次迭代都从内存重新读 flag
             cbz r0, .L2
        每次循环都走内存读，ISR 写进去的 1 就能被看到
      - **volatile 为什么能修复：**
        C 标准规定 volatile = "可能被程序无法看到的方式修改"（中断/DMA/硬件/另一线程）
        编译器被禁止对它做：缓存到寄存器、循环外提、常量传播、冗余读合并
        每次访问必须真正读写内存 → if 每次判断都取真值
      - 直觉类比：内存里的 flag = 公告栏，寄存器缓存 = 抄在便签上的旧值；非 volatile 只看便签（ISR 改公告栏看不到）；volatile 每次判断都去看公告栏
      - 边界注意：① ISR 里也要 volatile（否则编译器可能优化掉"看似无用的写"）② volatile 只解决"读新值"，不解决原子性（flag++ 仍会丢更新 → atomic/关中断）
    - **硬件寄存器(memory-mapped I/O)：**
      volatile uint32_t *pRCC = (volatile uint32_t*)0x40021000;
      *pRCC |= (1<<14);
      while(等待硬件置位HSERDY);
      寄存器会被硬件修改(状态位)且写有副作用，不能优化/合并
      - 一句话核心：volatile 对寄存器的意义≠普通变量的"读新值"，而是"读写都有副作用、必须真实执行"——重心完全不同
      - 编译器的两个危险假设（对普通变量成立，对硬件寄存器全不成立）：
        假设一：变量只在"源码写它的地方"改变 → 但状态寄存器是硬件随时置位/清零
        假设二：写只是"存值"，可被安全删除/合并/重排 → 但寄存器写会触发真实硬件动作
        volatile 就是强制编译器放弃这两条假设
      - **意义一·防"读旧值"——读不到硬件状态：**
        uint32_t *pSR = (uint32_t*)0x40000000;   // 非volatile
        while (!(*pSR & 0x01));   // 等硬件置标志位
        非volatile汇编：ldr r0,[r2]（循环外读一次）→ .L2: tst r0,#1 / beq .L2 → 永远用缓存值判断 → 死循环
        硬件置位了SR，但循环读的是寄存器缓存旧值 → 加volatile后每次 ldr 重新读内存才能看到
      - **意义二·防"删写/合并写"——保证写真实触发硬件：**
        寄存器写=触发动作（启动ADC/清中断标志/引脚输出电平/启动DMA搬运），写本身就是程序想要的行为
        非volatile时编译器按"写结果未被读过=死代码"删除只写不读的寄存器写 → 硬件动作没发生
        示例：*((uint32_t*)0x40012000) |= (1<<0);  // 启动ADC，只写不读 → 被优化掉 → ADC永远不启动
      - **读-改-写被缓存旧值破坏（清中断标志的大坑）：**
        EXTI->PR |= EXTI_PR_PR0;   // 写1清中断标志，硬件也会随时置位新标志
        编译成 LDR→ORR→STR 三步；非volatile用缓存"上次读的旧值"做ORR
        结果：清标志瞬间把硬件刚置位的新中断标志也一起写没 → 中断丢失
      - 为什么普通变量不需要 volatile：普通变量写只有"存储"语义，删除"未被读的写"行为不变；寄存器写本身就是目的，删掉行为就变
      - 一句话总结：volatile 对寄存器 = ①每次真实读内存（防缓存旧值、读不到硬件状态）②禁止删/合并/重排写（保证写动作真实打到硬件、触发副作用）。本质：编译器"变量只在源码处改变、写无副作用"的假设对寄存器不成立
    - **DMA 共享缓冲区：**
      volatile uint16_t adc_buf[128];  // DMA写、CPU读
      DMA是编译器看不见的写入者，必须volatile防读到缓存旧值
    - ISR 里用 i++ 需要原子操作吗？为什么很多代码只写 volatile？——单写者 vs 双写者辨析
      - 核心规则：单核上"读-改-写"安不安全 = 看能不能被"另一个也碰该变量的执行流"打断；ISR 执行期间主循环冻结（线程级无法打断中断）
      - **场景1·单写者（最常见，volatile 够）：**
        ISR 递增、主循环只读
        volatile uint32_t g_ticks;
        void SysTick_Handler(void){ g_ticks++; }   // 唯一写者
        int main(){ uint32_t t = g_ticks; }          // 只读
        g_ticks++ 的 LDR→ADD→STR 三步之间主循环被冻结，无法插入 → 天然不丢
        volatile 只负责让主循环读到真实内存值
      - **场景2·双写者（必须原子/关中断）：**
        ISR 和主循环都递增同一变量 → 丢更新
        main: LDR r0,[g_count] ←读到5 →（ISR打断）
        TIM_IRQ: LDR/ADD/STR → g_count=6 →（ISR返回）
        main: ADD r0,#1（还是断点前5）→ STR → g_count=6（覆盖ISR的+1，丢一次）
        两次递增最后结果6，丢一次更新；volatile 加了也救不了
      - **场景3·读+清（要临界区）：**
        ISR 递增、主循环"读后清零"
        uint32_t n = g_cnt;  // 读
        g_cnt = 0;           // 清 ← 读到和清之间被ISR打断 → ISR新加的被清掉 → 丢
        要：taskENTER_CRITICAL(); n=g_cnt; g_cnt=0; taskEXIT_CRITICAL();
      - 为什么很多代码只写 volatile：大多数真实场景恰好是单写者（tick计数/接收帧数/超时判断/事件标志，都是"中断里++/置位、主循环只读"），这类代码写 volatile 是对的
      - **两个隐患（"恰好对"≠"永远对"）：**
        ① 一旦加第二个写者（主循环也++、或更高优先级ISR也碰）→ 偶发bug极难排查（要抓时序才能复现）
        ② ISR 的 i++ 对"更高优先级ISR"不安全：高优先级可嵌套打断低优先级ISR的 LDR→ADD→STR → 同样丢更新
        volatile uint32_t g_cnt;
        TIM1_IRQHandler(){ g_cnt++; }  // 低优先级
        TIM2_IRQHandler(){ g_cnt++; }  // 高优先级，可打断TIM1的三步 → 丢
      - **判断 checklist：**
        1个写者 + 其他人只读 → volatile 就够（赋值单指令；i++ 靠单写者时序安全）
        ≥2个写者（不同执行流）→ 需要 atomic（LDREX/STREX）或关中断
        有"读+清/读+改"成对操作 → 需要临界区（读和写之间不能被插）
    - volatile 边界（什么时候加了也没用）：g_counter++ 是读-改-写管不住；g_flags|=BIT0 同理；多核可见性不保证（单核MCU不涉及）
  - **atomic 详细场景**
    - **多上下文共享计数器（ISR 和任务同时递增）：**
      volatile uint32_t g_packets=0;  // 错误示范：volatile不够
      ISR中：__atomic_add_fetch(&g_packets,1,__ATOMIC_RELAXED);
      任务中：uint32_t n=__atomic_load_n(&g_packets,__ATOMIC_RELAXED);
      递增=读→加→写三步，volatile会丢更新；atomic在CM3/M4编译成LDREX/STREX独占指令保证原子
      注意：Cortex-M0/M0+ 无LDREX/STREX，原子要靠关中断/软件实现
    - (b) 无锁单生产者-单消费者(SPSC)环形缓冲——详细解释
      - **场景：ISR 产数据入环、任务消费数据，双方"无锁"协作**
      - 机制：生产者只改 head、消费者只改 tail；各自原子写"自己指针"、原子读"对方指针"，避免数据竞争
        为什么用原子而不是volatile：① head/tail 更新要配合"数据可见性"顺序——生产者须"先写数据、再RELEASE发布新head"，消费者"ACQUIRE读head确认有数据、再取数据、最后写tail"；volatile 无内存序(RELEASE/ACQUIRE)语义，编译器/硬件可能乱序导致消费者读到未写完的数据
        ② head/tail 本身是"读+写"，volatile 管不住并发
        代码示例：
        __atomic_store_n(&ring.head, new_head, __ATOMIC_RELEASE);   // 生产者：发布
        __atomic_load_n(&ring.tail, __ATOMIC_ACQUIRE);              // 消费者：获取
        头尾不同时被一方写→无需锁，单核上极高效
      - **无锁 SPSC vs 互斥锁场景的区别**
        - 一句话区别：互斥锁靠"锁住共享区"排他访问（同一时刻只允许一个人进临界区）；SPSC 无锁靠"一写一读+原子发布/获取"从结构上避免竞争，全程无阻塞
        - **同步机制对比：**
          互斥锁：进临界区前加锁，出临界区解锁；锁本身解决"谁拥有访问权"
          SPSC无锁：没有锁，生产者只写head、消费者只写tail，各自原子读对方指针，用RELEASE/ACQUIRE内存序保证"数据写完才可见"
        - **适用场景对比：**
          无锁SPSC适合：ISR⇄任务（ISR里不能阻塞/不能拿锁）、单生产者单消费者、高频低延迟数据流（串口/DMA/ADC采样）、临界区极短（只动一个指针）
          互斥锁适合：多生产者/多消费者(MPMC)、临界区有复杂逻辑（不止改指针还要处理多变量）、访问频率低、需要睡眠等待（如信号量做任务同步）
        - 为什么 SPSC 能无锁：数据流单向——生产者写数据+发布head，消费者读head+取数据+写tail；head只被生产者写、tail只被消费者写，没有"同一地址双向竞争"；但"数据可见性顺序"仍需内存序保证，否则消费者可能读到未写完的数据
        - **对比表：**
          阻塞：互斥锁=会阻塞(拿不到锁等待) / SPSC=不阻塞
          开销：互斥锁=锁操作+可能上下文切换 / SPSC=一次原子写(RELEASE)+一次原子读(ACQUIRE)，极低
          竞争：互斥锁=锁竞争(同一时刻只一人) / SPSC=头尾分离无竞争
          死锁/优先级反转：互斥锁=有风险 / SPSC=无锁天然避免
          满/空处理：互斥锁=阻塞等待 / SPSC=直接返回(生产者丢帧/消费者空转，由调用方处理)
          数据可见性：互斥锁=锁自带内存屏障 / SPSC=必须显式RELEASE/ACQUIRE
        - **何时用哪个（决策）：**
          ISR⇄任务、单写单读、要最低延迟 → 无锁 SPSC
          多写多读、临界区复杂、可接受阻塞 → 互斥锁
          混用：核心数据管道用无锁SPSC，低频配置仍可用锁
          一旦变成多生产者或多消费者，SPSC无锁方案立即失效→退回互斥锁或更复杂的无锁算法
        - 关键前提提醒：SPSC 无锁不是"什么都不用做"，必须遵守内存序；单核上还要防编译器优化（head/tail 建议用 atomic 或 volatile）；只在"一写一读"时成立
    - (c) 状态机状态标志、跨任务统计量、tick计数——详细解释：
      适用对象：RTOS 中"多任务/ISR 同时访问的单个变量"且是读-改-写
      ① 状态机状态标志：多上下文迁移状态，必须原子"读状态-判断-改状态"
          // 原子CAS做状态转移，防止两个执行流同时转移
          __atomic_compare_exchange_n(&state, &expect, NEW_STATE, false, __ATOMIC_ACQ_REL, __ATOMIC_ACQUIRE);
      ② 跨任务统计量：如 g_active_tasks、g_packets，多任务/ISR 同时增减
          __atomic_add_fetch(&g_packets, 1, __ATOMIC_RELAXED);
      ③ tick 计数：如 g_cpu_ticks 运行时长统计，中断/任务同时更新
      选择原则：单变量+读-改-写 → atomic；多变量必须一起变 → 临界区
    - atomic 边界：只保护单个变量；要保护"多个变量一起变"(如坐标x/y、长度+指针)时原子无能为力→必须用临界区
  - **关中断（临界区）详细场景**
    - **多变量组合更新（必须原子地一起变）：**
      taskENTER_CRITICAL();
      g_pos.x = new_x;
      g_pos.y = new_y;   // x/y必须成对更新，不能被ISR打断在中间
      taskEXIT_CRITICAL();
    - 无原子平台的读-改-写替代（CM0上 flags|=BIT 非原子）：
      taskENTER_CRITICAL();
      g_flags |= FLAG_A;
      taskEXIT_CRITICAL();
    - **"读+清"必须成对（防丢数据）：**
      ISR每收到一帧置 g_frame_ready；主循环"读标志+清标志"必须原子
      否则ISR在"读"和"清"之间又置位，这一帧数据就丢了
      taskENTER_CRITICAL(); frame=g_frame; g_frame_ready=0; taskEXIT_CRITICAL();
    - **有严格时序的外设序列（不可被打断）：**
      __disable_irq();
      FLASH_Unlock(); FLASH_ProgramWord(...); FLASH_Lock();  // Flash编程时序
      // 或 I2C 起始/停止时序、SPI 收发配合
      __enable_irq();
      被中断打断会导致外设状态错乱
    - RTOS 内部队列/信号量结构保护：FreeRTOS 的 xQueueSend 内部就是用 taskENTER_CRITICAL() 保护队列结构不被多任务并发修改（临界区最普遍应用）
  - **选择决策树：**
    单次写/读一个值（硬件写、单步写）→ volatile
    单变量的读-改-写、要原子 → atomic（CM3/4）
    多变量/一段操作不可被打断 → 关中断/临界区
    ISR里要原子但尽量不关中断 → FromISR API + portYIELD_FROM_ISR
  - 注意事项：关中断时间必须短（否则影响 SysTick 和调度实时性）；ISR 里用 taskENTER_CRITICAL_FROM_ISR，且临界区内不能调用会阻塞的 API
  - **代码示例汇总：**
    volatile uint8_t g_rx_done=0; void ISR(){g_rx_done=1;}   // 单次赋值 volatile 足够
    __atomic_add_fetch(&cnt,1,__ATOMIC_RELAXED);               // 计数原子递增
    taskENTER_CRITICAL(); g_count++; taskEXIT_CRITICAL();      // 整段临界区
- 6. BootLoader 跳转 App 前为什么要关 SysTick、清中断、重设 VTOR？
  - 核心矛盾：中断是"事件驱动、随时可能来"的，而 App 的初始化是"顺序执行"的
    跳转完成 → App 把所有中断资源准备好，两者之间存在一段"空窗期"，遗留中断就在这个空窗期踩异常
  - **遗留中断为何会来**
    - BootLoader 使能过的外设跳转后仍在工作（串口还在收字节/定时器还在溢出/DMA还在搬运）→ 中断源依然有效
    - NVIC 使能位是内存映射寄存器，跳转不清除→原样保留；外设一产生事件 CPU 立刻进中断
    - App 的 main() 是顺序执行：SystemInit(时钟)→外设初始化→最后才使能中断；而跳转发生在 main() 之前
  - **踩异常的具体机制**
    - ① ISR地址/向量问题：没重设VTOR→中断跳BootLoader向量表，执行错误处理函数或跳非法地址→HardFault
    - ② 外设时钟未开：ISR一进来就访问外设寄存器(如USART1->DR)，但App的RCC时钟还没初始化(在SystemInit之后才开)→访问未使能时钟的外设→BusFault→升级HardFault
    - ③ 全局变量未初始化：ISR依赖的全局数组/标志还在 .data/.bss 拷贝清零阶段，读到垃圾数据→逻辑崩溃
    - ④ NVIC优先级分组不一致：BootLoader的分组/优先级与App不同，中断按旧优先级嵌套，产生不可预期抢占→栈错乱→HardFault
    - ⑤ 栈尚未就绪：跳转瞬间 MSP/PSP 设置不对，中断压栈压到非法地址→栈溢出→HardFault
  - **代码示例（空窗期）：**
    // BootLoader：
    USART_ITConfig(USART1, USART_IT_RXNE, ENABLE);  // 开了串口接收中断
    NVIC_EnableIRQ(USART1_IRQn);                     // 使能NVIC
    app_reset();  // 跳转（不清理上面）
    // App 刚启动：
    void Reset_Handler(void){ /* 拷贝.data、清.bss（ISR依赖的全局变量还没就绪）*/ main(); }
    void main(){
        // 此刻 USART 线上若已来一个字节 → USART1_IRQHandler 立即被调用！
        // 但 App 的 USART 时钟还没开 → ISR 访问 USART1->DR → BusFault
        SystemInit();   // 此时才配时钟
        USART_Init(...); USART_ITConfig(...);  // 此时才应开中断
        while(1);
    }
  - 为什么关 SysTick：BootLoader 用 SysTick 做延时，跳转后遗留中断会在 App 初始化前触发踩异常；SysTick->CTRL=0; SysTick->VAL=0;
  - 为什么清中断：跳转前必须清 NVIC 使能位(ICER)和挂起位(ICPR)——外设可能已有中断在排队等待，不清挂起跳转后立刻进中断；NVIC->ICER[i]=0xFFFFFFFF 清使能、NVIC->ICPR[i]=0xFFFFFFFF 清挂起
  - 为什么重设 VTOR：Cortex-M 靠 SCB->VTOR 定位中断向量表基址，App 在偏移地址（如 0x08008000），不重设则中断跳到 BootLoader 向量表→崩溃；SCB->VTOR=APP_BASE
  - **完整跳转函数：**
    void jump_to_app(void) {
        uint32_t app_msp = *(volatile uint32_t*)APP_BASE;      // 向量表[0]=App栈顶
        void (*app_reset)(void) = *(volatile void(**)(void))(APP_BASE+4); // [1]=Reset_Handler
        SysTick->CTRL = 0; SysTick->VAL = 0;                   // 1. 关 SysTick
        for (i...) { NVIC->ICER[i]=0xFFFFFFFF; NVIC->ICPR[i]=0xFFFFFFFF; } // 2. 清中断(使能+挂起)
        SCB->VTOR = APP_BASE;                                  // 3. 重设向量表
        __disable_irq();                                       // 4. 关全局中断再跳转
        __set_MSP(app_msp); app_reset();                       // 5. 设栈指针并跳转
    }
  - 注意事项：跳转前 __disable_irq() 更稳妥，跳转间隙也不被打断；过渡期看门狗要处理好避免被复位
- 7. 中断服务程序中调用 FreeRTOS 的队列或信号量 API 时，为什么必须指定中断安全版本（如 xQueueSendFromISR）？pxHigherPriorityTaskWoken 参数应如何正确使用？
  - **为什么必须用 FromISR 版本：**
    普通版会：① taskENTER_CRITICAL() 关中断，中断里再关中断冲突
    ② 队列满会阻塞等待（vTaskDelay 挂起"当前任务"，但 ISR 没有任务上下文，非法）
    ③ 可能直接 portYIELD 触发调度，破坏中断返回的栈帧和 EXC_RETURN
    FromISR 版：不阻塞（满返回 errQUEUE_FULL）、用 BASEPRI 掩码、唤醒高优先级任务时只记录不直接切换
  - pxHigherPriorityTaskWoken 标准用法：
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;  // ① 必须初始化为 pdFALSE
    xQueueSendFromISR(xUartQueue, &c, &xHigherPriorityTaskWoken); // ② 传入指针
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);   // ③ ISR 末尾按返回值决定是否调度
    若一个 ISR 多次调用 FromISR API：用同一变量累计，最后只 portYIELD_FROM_ISR 一次
  - 为什么必须看返回值：只有确实唤醒更高优先级任务（pdTRUE）才需要切换；无条件 yield 是多余切换开销
  - **portYIELD_FROM_ISR 的本质：**
    #define portYIELD_FROM_ISR(x)  portYIELD_IF_ISR(x)
    #define portYIELD_IF_ISR(x)    if (x != pdFALSE) { portYIELD(); }
    portYIELD() = 往 ICSR（0xE000ED04）的 PendSV 置位位（bit28）写1 → 挂起 PendSV 异常
    本质是"预约一个切换"，并不直接切换任务
  - 为什么用 PendSV：PendSV 优先级被配为最低，ISR 能正常返回→硬件恢复现场→返回任务前发现 PendSV 挂起→进 PendSV handler 做真正切换；把调度推迟到所有高优先级中断处理完，不影响中断实时性
  - 上下文切换实现（xPortPendSVHandler 汇编核心）：
    mrs r0, psp  → 取当前任务栈指针
    stmdb r0!, {r4-r11, r14} → 保存现场到任务栈
    str r0, [r2] → 栈顶存回 TCB->pxTopOfStack
    msr basepri → 关中断；bl vTaskSwitchContext → 选最高优先级任务更新 pxCurrentTCB
    恢复新任务栈 → bx r14 异常返回，硬件从新栈弹 PC/xPSR/LR
    每个任务现场存在各自任务栈，PendSV 只做"旧现场压栈 + 新现场出栈"
  - 为什么不能等下一个 tick：不主动 yield，被唤醒任务要等下一个 SysTick（如 1ms）才调度，最坏延迟接近 1 个 tick；实时性敏感场景（帧解析/电机控制）会丢帧失控；portYIELD_FROM_ISR 让 ISR 一返回就切换
  - **代码示例（UART 中断 + 队列）：**
    void USART1_IRQHandler(void) {
        BaseType_t xHigherPriorityTaskWoken = pdFALSE;
        uint8_t c = USART_ReceiveData(USART1);
        xQueueSendFromISR(xUartQueue, &c, &xHigherPriorityTaskWoken);
        portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
    }
- 8. MCU 内部 Flash 模拟 EEPROM 时，写入前必须执行页擦除，但擦除操作时间较长（ms 级）。如何在擦除期间不影响系统其他中断响应，并保证数据完整性？
  - 问题根源：擦除期间 Flash 控制器被占用，CPU 从 Flash 取指会 stall；中断向量/ISR 在 Flash 里→中断响应被延迟
  - **方案一：代码放 RAM 运行**
    把"擦除+写"函数和中断服务函数放 RAM 段（GCC: __attribute__((section(".ramfunc")))，Keil: __RAM_FUNC），擦除期间取指不 stall
    // 示例
    __attribute__((section(".ramfunc")))
    void flash_erase_page_ram(uint32_t page_addr) {
        FLASH_Unlock(); FLASH_ErasePage(page_addr); FLASH_Lock();
    }
  - 方案二：硬件自动暂停——STM32F4/F7 等：擦除中来了中断，硬件自动暂停 Flash 操作先响应中断，返回后自动继续擦除（响应略延迟不丢失）；F1 无此机制更依赖方案一
  - **数据完整性三招：**
    ① 擦除前先把整页要保留的数据备份到 RAM/另一页
    ② 双页交替冗余：轮流写页A/页B，页头记有效标志+CRC，任何一步掉电都能从另一页恢复
    ③ 写后回读校验（CRC/逐字节比对），不一致则重写
  - **代码示例（双页冗余最小逻辑）：**
    flash_write_reliable(new_data) {
        backup = (active_page==PAGE_A)?PAGE_B:PAGE_A;
        flash_erase_page_ram(backup);            // 1. 擦备份页（RAM版，中断不受影响）
        flash_write_word(backup, new_data);
        flash_write_word(backup+4, crc(new_data));
        if (read(backup+4) != crc(new_data)) return ERROR; // 2. 回读校验
        flash_write_word(MAGIC, backup); active_page = backup; // 3. 切有效标志
    }
    核心原则：任何时刻至少有一个页的数据完整可校验
- 9. 看门狗（IWDG / WWDG）在低功耗模式下（如 STOP 或 STANDBY）的行为有何不同？唤醒后喂狗失败通常由哪些原因导致？
  - **差异核心：**
    IWDG（独立看门狗）：LSI 驱动，STOP/STANDBY 下 LSI 保持运行，IWDG 照常递减→睡眠中可能被复位；一旦使能无法软件关闭
    WWDG（窗口看门狗）：PCLK1 驱动，低功耗下 PCLK 停止，WWDG 停止计数；唤醒后重新运行；可软件关闭
  - 常见坑：进入 STOP 前把 IWDG 喂到满值，但睡眠时间超过超时周期→睡着睡着被复位；唤醒后第一件事必须重新喂狗
  - **喂狗失败原因：**
    ① 唤醒后时钟未就绪（HSE 起振/PLL 锁定）喂太晚  ② 睡眠时间估算错误超时
    ③ 主循环被阻塞（等待外设/死循环）喂狗没机会执行  ④ 被高优先级中断长时间打断
    ⑤ 仿真器暂停 CPU 时 IWDG 仍在跑，暂停久了照样复位  ⑥ WWDG 窗口把握错（太早/太晚都复位）
    ⑦ STANDBY 唤醒=复位，需重初始化时钟/外设/喂狗，顺序错会复位  ⑧ LSI 漂移约±15% 边界算错
  - WWDG 窗口规则：必须在窗口内喂，太早（计数器未降到下窗）或太晚（降到0）都触发复位
- 10. 使用外部晶振（HSE）时，若起振失败，硬件或软件上应如何检测并自动切换至内部 RC（HSI）？切换过程中需要注意哪些时钟依赖问题？
  - **检测方式：**
    软件轮询：开 HSE 后等 HSERDY 标志，超时判定起振失败
    硬件 CSS（时钟安全系统）：HSE 起振失败或运行中失效自动产生 NMI 中断，可进 NMI 切 HSI，比轮询可靠
  - **软件切换流程：**
    ① 先关 PLL → ② 切 SYSCLK 到 HSI（HSI 始终就绪）→ ③ 按 HSI=8MHz 重算倍频配 PLL → ④ 开 PLL 等 PLLRDY → ⑤ 可切回 PLL → ⑥ 更新 Flash 等待周期
  - **CSS 的 NMI 处理：**
    void NMI_Handler(void) {
        if (RCC_GetFlagStatus(RCC_FLAG_CSS)) {
            RCC_SYSCLKConfig(RCC_SYSCLKSource_HSI);
            RCC_ClockSecuritySystemCmd(DISABLE);  // 关 CSS 防反复进 NMI
            RCC_ClearFlag();  /* 重新配 PLL 以 HSI 为源 */
        }
    }
  - **时钟依赖问题：**
    ① PLL 必须先关再按 HSI 重配，否则锁在失效 HSE 上  ② USART/ADC/定时器等外设频率变，需重算波特率/采样率
    ③ Flash 等待周期（Latency）要同步更新  ④ AHB/APB 分频值要匹配
    ⑤ CSS 切后要重新评估  ⑥ USB 48MHz 可能失步需切换时钟源
- 11. Cortex-M 的 MPU（内存保护单元）如何配置可防止堆栈溢出或非法指针访问？开启 MPU 后，为什么通常需要把关键外设区域设置为"设备"或"强排序"类型？
  - MPU 能力：Cortex-M3/M4 提供 8 个区域（M7=16），可配基址/大小/权限/类型/缓存/XN；访问违规触发 MemManage Fault，比 HardFault 更易定位且粒度更细
  - 防堆栈溢出：给任务栈划 MPU 区域+栈底设"禁止访问"保护区，栈向低增长越界踩进保护区→MemManage→故障处理可定位哪个栈溢出（FreeRTOS-MPU 做法）
  - 防非法指针访问：代码跑在非特权模式，MPU 限定每个任务可访问范围，野指针/越界/执行非法内存被拦截→MemManage 而非静默写坏内存
  - **配置流程与代码：**
    MPU->CTRL=0（关）→ RNR/RBAR/RASR 逐区域配置 → CTRL 开 + PRIVDEFENA
    区域0=任务栈底保护区（AP=无权限）；区域1=外设区 0x40000000（Device 类型）
    MPU->CTRL = ENABLE | PRIVDEFENA;  DSB(); ISB();
  - **为什么外设要 Device/强排序：**
    Normal 类型允许写合并/缓存/乱序→灾难：
    ① 连续两次写同一寄存器被合并，第二次写丢失
    ② 有顺序依赖的写被重排（先写控制A再写数据B）
    ③ 读状态寄存器被缓存读不到真实硬件
    Device：不可缓存/不可重排/不可合并，保证每次读写真实打到外设；Strongly Ordered 更严格，按程序顺序立即访问，用于时序苛刻场合
- 12. MCU 进入 HardFault 后，如何通过栈帧（PSP/MSP）反推现场 PC 和 LR 值？哪些常见编程错误（如未对齐访问、除零、外设时钟未开）容易触发该异常？
  - 判断栈：异常进入时 LR 是 EXC_RETURN，bit2=0 用 MSP（异常/内核上下文），bit2=1 用 PSP（任务上下文）
  - 读栈帧：硬件自动压栈 8 字（栈顶→底：R0,R1,R2,R3,R12,LR,PC,xPSR）；sp[0..7] 对应；PC=sp[6] 出错指令地址，LR=sp[5] 调用来源
  - **代码示例：**
    void HardFault_Handler(void) {
        __asm volatile(" TST LR,#4 / ITE EQ / MRSEQ r0,MSP / MRSNE r0,PSP / B HardFault_Analyze ");
    }
    void HardFault_Analyze(uint32_t *sp) {
        uint32_t lr=sp[5], pc=sp[6], xpsr=sp[7];
        printf("HardFault @ PC=0x%08X LR=0x%08X\n", pc, lr);  // 反汇编定位出错行
    }
  - **常见触发错误：**
    ① 未对齐访问（M0/M0+ 不支持；M3/M4 默认支持但某些 DMA/MPU 区域仍会 BusFault）
    ② 除零（未开 DIV_0_TRP 返回0；开了触发 UsageFault）
    ③ 外设时钟未开就访问寄存器→BusFault→升级 HardFault（最常踩）
    ④ 空指针/野指针访问未映射内存  ⑤ 栈溢出  ⑥ 非法指令/跳错地址
    ⑦ 中断使能但向量地址错  ⑧ MPU 下特权级非法操作
  - 故障升级机制：MemManage/BusFault/UsageFault 处理函数不可用或优先级冲突时，会升级为 HardFault（"怎么改都进 HardFault"先查子 Fault 是否被屏蔽）

  面试官您好，我叫陈志豪，是深圳大学电子信息工程专业2027 届应届生，来应聘贵司的嵌入式软件工程师岗位。
  以下是我的个人简介。
  首先介绍实习相关的部分：
  我之前在深圳乐动机器人担任嵌入式开发实习生，参与割草机器人整机项目的开发与维护。工作内容主要有以下几点：
  第一是独立负责新项目外设板的开发，主要是驱动开发以及数据传输。驱动开发包括根据数据手册对AHT20 温湿度、MLX90642 红外热成像两路 I2C 设备进行开发，以及将算法板的红外回充解码相关代码移植到外设板上，数据传输部分主要是与应用组的同事在原来项目的数据传输框架下定义新增模块的具体协议。驱动代码经团队评审后合入主分支，支撑了量产验证阶段按期推进。
  第二是负责老机器的边缘功能开发，主要包括新imu的适配和静音功能的完善。
  第三是处理测试 BUG 与客诉问题单，处理总问题数达30+，嵌入式相关问题80%以上当天闭环，涉及跨组复杂问题会输出嵌入式层面的根因分析，然后移交对应的同事进行下一步的分析。
  第四主要是一些突发问题的处理。
  然后是项目相关部分：
  课外我独立完成了两个项目：一个是基于 STM32 双 MCU 和 CAN 总线的智能中控面板，使用 FreeRTOS 做 8 任务分层，CAN 发送任务配合 peek 机制做到不丢帧、不乱序，同时用 LVGL 实现了仪表盘 UI 和 YMODEM 协议的 OTA 升级；另一个是基于 ESP32 和 FreeRTOS 的天气时钟项目，过**串口 AT 命令**控制 ESP32-C3 模块，连接 WIFI 网络获取温度和实时时间。通过rtos队列实现了ui的异步串行处理，以及任务区分前后台。
  最后是我的技术栈：
  我熟悉 C 语言、STM32、FreeRTOS 以及 I2C、SPI、UART、CAN 等常见总线，动手能力和根因分析能力比较扎实，希望有机会加入贵公司，谢谢。
