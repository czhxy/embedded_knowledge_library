## C语言基础
- **数组与指针的区别**
  - **自我评价：答得不好 ⚠️**
  - **正确回答：**
    - **1.数组和指针包含的数据内容不同。**
      数组内是数据实体，如int、char等类型的数据。指针的数据是地址，该地址指向的内存空间才存储着数据。
    - **2.占用的内存大小不同。**
      用sizeof输出数组的大小，比如int a[4];那么大小就是4*4=16B，但是指针的大小用sizeof输出则一直是固定的，在32位单片机中为4字节
      - **这里引出一个嵌入式开发中的坑。**
        函数形参中的“数组彻底退化”
        在函数参数中，void func(uint8_t arr[100]) 写法是语法糖，编译器会强制将 arr 退化为 uint8_t *arr。
        在函数内部，sizeof(arr) 不再是100，而是4（指针大小）。
        所以切记数组长度必须显式通过第二个参数传入。
        并且此时这个arr变成了左值（变量），可以对函数内的这个形参指针进行 arr++ 操作（移动指针），而外面的数组基址不受影响。
    - **3.存储的位置不同**
      - 1.数组的空间在编译时就确定了。根据局部和静态的区别分布在栈上或者全局静态区内。分配时间固定
      - 2.指针变量本身在栈或者静态区，但是它指向的内容可以来自任何地方（栈、静态区、malloc堆）。如果指向堆，malloc的耗时是不确定的（引出实时操作系统相关的知识）
        - **对于rtos来说，任务的创建主要是动态创建和静态创建。**
          对于动态创建：
          调用xtaskcreate时，内核内部调用pvportmalloc从堆中挖出一块内存作为栈，内核拿到的只是一个内存地址（指针）。
          由于使用pvportmalloc，分配的时间是不确定的，这对rtos来说是非常不好的。
          对于静态创建，栈是提前定义好的静态数组，任务创建时会退化成指针交给内核。
          静态创建的优势就是这块内存时编译时就确定的，分配耗时零抖动，并且不会产生碎片
    - **4.地址的连续性**
      - 数据分配的是一块虚拟地址连续、物理地址也连续的内存块。可以直接将首地址交给DMA进行控制。
        指针：如果指针指向的是通过malloc分配的内存。
        若是堆管理器分配的地址是连续的就没问题，但是若是指向了分散的链表节点或者结构体成员，那就不能使用dma进行搬运。
- **数组与链表的区别、开发中的使用场景**
  - **自我评价：答得不好 ⚠️**
  - **正确回答：**
    - **1.内存分配与碎片。**
      数组是静态分配的，编译时大小就已经确定，占用连续内存块，并且根据局部还是全局和静态分配在栈或者全局/静态区中。数据没有内存碎片的问题。
      链表是动态分配的，节点随意散布在堆中，靠指针维系。
      由于是动态分配的，频繁的malloc和free可能造成内存碎片，碎片累计到一定程度就会导致分配失败
    - **2.操作的确定性**
      数组查找的耗时是确定的，时间复杂度为O（1）
      链表的查找时间是不确定的，这对于rtos中是不可接受的
    - **3.风险**
      栈溢出与内存安全
      数组：最大的风险是数组越界。一旦越界，会直接踩坏栈帧或相邻变量，引发HardFault硬错误，调试难度极大。
      链表：最大的风险是野指针和内存泄漏。指针操作失误，会导致系统逻辑混乱；若忘记释放，长时间运行内存会耗尽。
    - **为什么FreeRTOS会大量使用链表：**
      - **1. 核心原因：任务调度本质是“队列管理”**
        - 操作系统的调度器本质上是一个动态优先级队列。任务会随时挂起、恢复、阻塞、超时。
          如果用数组管理任务控制块（TCB），插入或删除一个任务需要搬运大量内存，时间复杂度 O(n) 且伴随耗时的大块数据拷贝，这会直接拉长中断关闭时间。
          用链表（双向链表），插入和删除节点只需修改指针，时间复杂度 O(1)。对于实时内核来说，这种“插入/删除”的极速操作比“随机访问”重要得多。
      - **2. 消除“查找不确定性”的大杀器：优先级位图**
        - 这是最关键的反直觉点。你说链表遍历查找是 O(n) 的不确定性，但 FreeRTOS 几乎从不遍历链表去查找下一个要运行的任务！
          它使用了一个 32 位（或 64 位）的变量 uxTopReadyPriority 作为位图（Bitmap）。
          当某个优先级有任务就绪时，对应的 bit 位被置 1。
          调度时，直接通过硬件前导零指令（CLZ）或查表法，在 O(1) 的常数时间内算出当前最高优先级。
          拿到优先级后，直接用该优先级作为数组下标，从 pxReadyTasksLists[priority] 中取出链表的第一个节点。
          结论：FreeRTOS用“位图 O(1) 查优先级 + 链表 O(1) 取任务”的组合拳，彻底抹掉了遍历链表的不确定性。
      - **3. 静态内存池，把“碎片”扼杀在摇篮里**
        - 我之前警告“不要用 malloc 创建链表”，FreeRTOS 严格遵守这一点。
          FreeRTOS 的链表节点（ListItem_t）并不是单独 malloc 出来的。
          它是侵入式链表，节点直接内嵌在任务控制块（TCB）、软件定时器或事件标志组这些静态分配的结构体内部。
          所有 TCB 要么在编译期静态分配（configSUPPORT_STATIC_ALLOCATION），要么在启动时从预先划好的大堆栈中一次性分配。任务运行期间，绝不动态创建或销毁链表节点，所以根本不存在内存碎片风险。
      - **4. 临界段保护，锁死“时间不确定性”**
        - 链表操作的不确定性还在于操作过程中可能被中断打断。FreeRTOS 的解决方案极其硬核：
          所有对链表的插入、删除、查找操作，都包裹在临界区（taskENTER_CRITICAL()）或调度器挂起（vTaskSuspendAll()）中。
          在此期间，系统关中断或禁止任务切换。这就保证了对链表的操作是一个原子操作，虽然会暂时延长一点中断响应延迟，但换来了操作时间的绝对确定性上界（即执行固定几条指针赋值指令的时间）。
- **哈希表的原理**
  - 定义：hash table 是一种实现O(1)平均时间复杂度读写的数据结构，
    核心是“键（key) ->hash值->下标的映射机制”
  - **核心策略：这是一种空间换时间的策略。**
  - 存储原理：hash表维护一个内部数组，当插入一个键值对时，你不需要遍历整个链表，
    只需要根据键值就能计算出它在数组的哪个位置，读取时也是同样，
    可以直接计算出要读取的位置
  - 核心引擎：hash函数。它接收任意类型的key（字符串、对象），
    然后输出一个hash值，同样的输入一定会得到同样的hash输出。
  - **核心难题：hash冲突，不同的输入可能得到同一个输出，**
    但是不能放在同一个位置。
  - **解决冲突（两个办法）**
    - **开放寻址：找下一个非冲突的格子**
    - **链地址法：在数组的每一个格子存一个链表，**
      发生冲突时将这个格子挂在链表尾

## RTOS
- **介绍对rtos的理解，裸机多任务和rtos多任务的区别**
  - **自我评价：答得一般⚠️**
  - **正确回答：**
    - 定义：rtos是带任务调度、时间管理和任务通信机制的操作系统内核（如FreeRTOS），核心价值是“确定性 + 多任务并发”。
    - **裸机多任务 vs rtos多任务的区别：**
      - 任务调度方式：裸机是“伪多任务”（前后台系统，主循环+中断，靠状态机/标志位手动切换）；rtos由内核按优先级抢占式调度
      - 时间确定性：裸机任务响应时间依赖主循环周期，不可控；rtos通过优先级抢占保证关键任务在确定时间内被调度
      - 任务通信：裸机只能靠全局变量（有原子性风险）；rtos提供队列/信号量/事件组
      - **引入新风险：死锁、优先级反转、栈溢出、任务间耦合**
    - **rtos相对于裸机的优势：**
      - **1.实时性。**
        通过抢占任务优先级以及时间片轮转时间等的合理设置可以实现高实时性，让高优先级的任务可以实现优先运行，且每个任务的执行时间都能得到保证。
      - **2.提高多任务项目的开发效率。**
        多任务的项目中经常会设计到数据竞争的问题，对于裸机来说需要使用加锁，关中断等方式才能避免数据的撕裂，
        同时对于并行多任务执行，还需要复杂的调度机制，来确保每个任务都能有对应的执行时间，同时还要根据任务的优先级来制定执行顺序。
        那这些开发的内容在rtos中都帮你做好了，所以开发者需要关注每个任务要执行什么内容，以及任务间的通信就好了，减少了很多代码量。
    - 当然裸机的优势就是省内存，当项目资源比较紧张时，那就不得不使用裸机了。
- **rtos实时性如何保证？**
  - 怎么确保每次时间一样？若是4ms周期任务需要花费10ms会发生什么？
    - **使用定时器任务或者使用xtaskdelayuntil。**
      若有高优先级任务，该任务会导致被打断，
      若是该任务就是最高优先级任务，那么就无法让出cpu，别的任务得不到执行
    - **完善补充：**
      - 核心结论：单次耗时（10ms）超过周期（4ms）→ 周期漂移、错过下一周期，实时性失效
        - **定时原理：xTaskDelayUntil是绝对延时，**
          下次唤醒时刻 = 上次计划唤醒 + 周期，
          按0/4/8/12ms固定刻度唤醒，不累积误差
        - 出错过程：任务0ms开始执行第1轮（prev=0），4ms/8ms唤醒点被错过；
          10ms执行完调vTaskDelayUntil(prev=0,4)→目标4ms已过→立即返回不阻塞，
          任务无缝进入第2轮（10~20ms），12ms/16ms唤醒点同样被错过
        - xTaskDelayUntil行为：目标唤醒时刻已过 → 立即返回不阻塞 → 形成忙循环，几乎不停歇
        - 后果①错过唤醒点：周期失效，采样/控制频率从250Hz跌到100Hz
        - 后果②周期漂移：vTaskDelay相对延时每轮“跑10ms+睡4ms”，
          实际周期变14ms且累积偏移
        - **后果③占死CPU：其他任务饿死**
          （呼应原始回答：最高优先级任务无法让出cpu）
        - **本质：不可调度**
          实时性=任务必须在周期（deadline）内完成；
          CPU利用率=执行时间/周期=10ms/4ms=250%>100%，
          结构性失败，不是偶尔超时
      - 正确解法：拆分任务，用状态机分段执行，保证每个周期内占用时间 < 周期时间
      - xTaskDelayUntil（绝对延时，下一次唤醒=上次+周期，不累积漂移，适合固定周期任务）
        vs
        vTaskDelay（相对延时，睡眠固定时长，会累积误差）
  - **除了设置高优先级外还有什么方法？**
    - 非常重要的任务就设置高优先级中断，中断比任何任务的优先级都要高，靠中断可以保证最快的响应。
      如foc控制，高频的且需快速进行响应就需要使用中断实现
    - **完善补充：**
      - **配置tick时钟节拍频率，决定时间精度**
      - **高优先级任务必须短小、非阻塞（避免长延时、阻塞式IO）**
      - **临界区/调度锁尽量短，降低关中断时间和中断延迟**
      - **避免在任务里malloc（耗时不确定）**
      - **中断里只做快速处理（置标志/给信号量），重活放任务；**
        响应时间 = 硬件中断延迟 + 上下文切换时间

  - **普通量跟二值信号量的区别**
    - **自我评价：答得不好 ⚠️**
    - **正确回答：**
      - **1.等待机制（这也是最大的区别）**
        普通量想要读到标志只能不断的通过轮询读，这是十分占用cpu的，但是二值信号量有阻塞机制，
        在没有等到信号量时会被放进阻塞列表里，不影响cpu，
        当接收到信号量时，由于有xTasksWaitingToSend和xTasksWaitingToReceive的双向链表机制，可以准确进行快速唤醒
      - **2.原子性与临界保护**
        变量的读写改并不是一条指令。
        不同变量若有中断和高优先级的任务访问的情况下，可能在执行到一半时被打断，造成数据错误，
        所以普通变量在这种情况下需要注意使用关中断或者加锁的方式进行保护。
        二值信号量自带临界保护，它的操作是在临界区内执行的，操作是线程安全的
      - **3.中断同步的效率（isr场景下）**
        普通变量：在 ISR 中置 1 后，任务不知道何时去读，除非任务一直轮询（这极不推荐，会卡死低优先级任务）。
        二值信号量：在ISR 中调用xSemaphoreGiveFromISR() 并传入 pxHigherPriorityTaskWoken，
        RTOS 能在中断退出时直接切换上下文，立即执行等待该信号量的高优先级任务，
        中断响应和任务处理无缝衔接。
      - **4.功能语义与承载信息：**
        二值信号量是bool类型的，只能传递0和1。
        普通变量可以传递不同的数值，代表不同的含义
      - **5.内存与系统开销：**
        普通量的内存开销极小。
        二值信号量开销较大，需要几十字节的ram
      - **6.经典的“优先级反转”风险**
        - 定义：低优先级任务占着共享资源，导致高优先级任务被阻塞在它后面，中优先级任务趁机抢占，系统实时性劣化
        - 解决：优先级继承 / 优先级天花板；二值信号量本身不防反转，需使用互斥量
      - **补充：二值信号量 vs 互斥量（mutex）**
        - 互斥量有所有权（谁拿谁释放），支持优先级继承，适合互斥保护共享资源
        - **二值信号量用于同步（生产者/消费者通知），没有所有权**
      - 补充：任务通信更常用队列（Queue），能携带数据；信号量只传状态不传内容
## CAN总线
- **CAN错误处理**
  - **自我评价：回答太过简单 ⚠️**
- 做一个can盒：5M串口和1M can转换怎么处理、要注意哪些坑
  - **一、核心矛盾：速率倒挂 ⚠️**
    - 串口 5Mbps（8N1）：每字节 10bit（1起始+8数据+1停止），有效吞吐 = 5M/10 = 500KB/s
    - CAN 1Mbps（标准帧 11bit ID + 8字节数据）：一帧约 130bit（含位填充），8字节/130us ≈ 60KB/s
    - 结论：串口比 CAN 快约 8 倍，串口→CAN 方向是「粗进细出」，无流控+缓冲必丢帧；CAN→串口方向无压力
  - **二、整体架构**
    - PC上位机 ──5M UART(500KB/s)──► MCU ──1M CAN(60KB/s)──► CAN总线
      中间靠大环形缓冲 + 流控吸收速率差
  - **三、5M 串口处理要点**
    - 波特率精度：5Mbps 下 1bit=200ns，累计误差>±2% 采样错位，晶振要 ±50ppm 以内，BRR 分频误差要实算
    - 过采样模式：16x 需 UART 时钟≥80MHz（很多 MCU 挂低速 APB 跑不到）；8x 只需 40MHz，5M 更稳（抗噪略差）
    - 例：STM32F407 USART1/6 在 APB2(84MHz)，16x 上限仅 5.25M 贴极限，强烈建议 8x 过采样（上限 10.5M）
    - 上位机芯片坑：CH340/FT232R/CP2102 最高只到 2~3M，跑不了 5M；需 FT232H(12Mbaud)/CH343(6M) 这类高速芯片
    - 接收方式：500KB/s = 每字节 2us，禁用逐字节中断；必须 DMA + 空闲中断(IDLE)，半满/全满切缓冲
  - **四、1M CAN 处理要点**
    - 位时序：1Mbps 推荐采样点 75%~80%，BRP/Tseg1/Tseg2/SJW 按采样点公式配，别用默认值
    - 收发器+终端电阻：用 CAN 专用收发器（TJA1050/1042），总线两端各 120Ω 终端电阻
    - **总线长度：1Mbps 上限约 40m（ISO 11898）**
    - 吞吐再确认：上位机满速 500KB/s 会打爆 CAN 发送队列，需限速或背压
    - CAN FD 选项：数据量大建议 FD（仲裁段 1M + 数据段 5M/8M，单帧 64 字节），大幅缓解速率倒挂
  - **五、串口↔CAN 协议设计**
    - SLCAN（ASCII）：如「t1238」+ 回车发标准帧；兼容 socketcan/can-utils，调试方便；但 8 字节数据膨胀成约 20 字节 ASCII，串口利用率低
    - 自定义二进制：帧头+长度+ID(4B)+标志+data+CRC；效率高，适合 5M 满速，需自己写解析
  - **六、缓冲与流控（设计核心）**
    - **环形缓冲：串口接收、CAN 发送各一个，容量按最坏积压算**
    - 背压/流控：CAN 发送队列快满时拉低 RTS（硬件流控），或 XON/XOFF（软件流控），让上位机暂停发送
    - **溢出策略：缓冲满要明确丢弃策略 + 丢帧计数上报，不能静默丢**
  - **七、坑清单（速查）**
    - 1. 先验证 MCU 的 UART 和 USB 转串口芯片都真能跑 5M
    - 2. 波特率误差要实测（示波器看 bit 宽度），别只看寄存器
    - **3. 串口接收必须 DMA+IDLE，禁用逐字节中断**
    - **4. 速率 8:1 倒挂，串口→CAN 必须流控，否则丢帧**
    - **5. CAN 采样点按 75%~80% 配**
    - **6. 数据量大优先上 CAN FD，否则 CAN 是瓶颈**
    - **7. 串口协议加 CRC + 明确帧边界，丢帧可检测**
    - **8. 终端电阻、总线长度按 1Mbps 规范来**
