## 3. 最难 Bug｜机器上桩堵转
- **现象：机器在桩上发生堵转**
  （正常上桩进入充电时轮子不应有速度，不应出现堵转）
- **复现：在专门测试场地测试，公司内无法复现**
- **日志：提取机器运行日志**
- **排查过程**
  - **① 根据电机电流确认是否真的发生堵转**
  - **② 确认堵转后看感知结果，找堵转原因**
    同一机器发生三次：
    - 两次待机时堵转（过程不完整，感知看不出问题，一直在桩上）
    - 一次触发悬空（有完整上桩→堵转全程，从此日志最终确认；前两个只能怀疑是对桩异常）
  - **③ 查看机器为何持续运动（正常应停住）**
    状态标识一直处在上桩回充状态而非开始充电
    说明一直在尝试对桩但没对上，持续怼桩导致堵转（怼桩是机器执行策略）
  - **④ 从完整日志看出：上桩角度明显不对导致不能识别上桩**
    上桩规划属算法部分
- **根因与贡献边界**
  - 根因：上桩角度异常 → 一直无法识别上桩 → 持续怼桩 → 堵转
  - 我的贡献：多源日志交叉定位，排除外设层（电机驱动/红外对桩/硬件）嫌疑
    定位到上桩角度异常，形成完整证据链后移交算法团队
  - **最终修复：由算法团队优化上桩规划完成**
- **验证结果：算法优化上桩规划后，后续版本未再出现类似问题**
- **难点**
  - **干扰因素多：**
    - 两个符合描述的 bug 日志恰好缺少关键上桩过程
    - 所有 bug 都附带悬空报错，增加排查难度
## 4. 外设板数据接收机制
- **当前外设板主要是发送数据**
  接收只收 OTA 数据
- **接收方式：中断**
  - **每收到一个字节进一次中断，拼成完整帧后送入回调处理函数**
- **协议处理**
  - 用同一套通信框架：帧头 + 帧尾 + mod_id + mod 长度 + crc校验
    可避免半包、粘包问题
  - **校验错误：不接收该包数据**
  - **接收超时：最长 180ms，超时退出**
  - **重复包：暂时没有相关处理**
  - **当前板只管发送**
## 5. ESP32 双电机 FOC 项目
- **电机：2208**
  驱动器：套件
  电流传感器：INA240A
  位置传感器：AS5600 磁编码器
- **控制周期：电流环 20k（ISR 内执行）**
  速度环 1k（电机控制任务内）
  位置环 200Hz（电机控制任务内）
- **ADC 采样与 PWM 同步**
  - **① 节拍同步：同一个 20kHz 定时器**
    TIMG1 硬件定时器以 20kHz（50µs）触发 foc_timer_isr_entry → foc_isr
    电流采样、电流环 PID、SVPWM 输出全在这一次 ISR 内顺序执行，没有跨周期缓冲
    天然同一节拍——不存在“采样靠别的时钟”的问题
  - **② 采样点对齐：软件延时到 SVPWM 下管导通中点**
    PWM 中心对齐，三相占空比关于周期中点对称
    周期中点附近存在“三相下管全导通”的公共窗口
    此刻相电流经采样电阻方向稳定、无开关瞬态，是理想的电流采样点
- **FreeRTOS 任务划分（3 个任务）**
  - ① 电机控制任务：AS5600 位置更新 + 速度环/位置环计算
    接收串口任务发来的简短指令
  - ② 解析串口指令任务：解析上位机指令，通过队列发给电机控制任务
  - **③ 监控任务：周期打印心跳及电机状态**
## 6. YMODEM 升级与恢复
- **一、传输中断（拔线/掉电/超时）**
  - 每包有超时；CRC/序列/超时错误 → NAK + 重试，最多 10 次
  - **超限放弃：ota_ymodem_start() 返回**
    boot 进入 while(1)，3 秒后重试
  - 掉电/拔线重启：接收全程 ota_state 始终是 IDLE
    （RECEIVING/VERIFY 是 dead code 从未置位），只有全部成功后才会写 COMPLETE
  - 重启后 boot_decision 走 IDLE 分支 → 活跃槽有效 → 直接跳旧固件
  - **目标槽残留半镜像无影响：元数据（size/crc）还是旧的**
    下次 OTA 会重新擦除覆盖
- **二、Flash 写入中断**
  - F4 的 Word/Byte 编程是原子操作，不存在“写一半”
    要么整字完成要么硬件报错；每字写完还有回读校验
  - 写入失败：flash 返回 YMODEM_ERR_FLASH → 中止，活跃槽不变
  - **擦除/编程中掉电 → 该扇区内容不确定，但只发生在非活跃槽**
  - **参数区掉电由 append-only 日志兜底**
    （写半条 → CRC 不匹配 → load_latest 跳过取上一条）
- **三、整包校验失败（两层）**
  - 逐包 CRC16（协议层）ymodem.c:101：每 1024B 包校验，失败 NAK 重试
  - 整包 CRC32 + reset-handler 防错包 ota.c:94-103：
    检查镜像链接地址是否落在目标槽（防发错 bin）；算 CRC32 后记录到元数据
  - 关键点：算完 CRC32 后没有立即与期望值比较，直接翻转 active
    真正整包校验被推迟到下次启动的 boot_decision COMPLETE 分支
  - CRC32 mismatch → boot_count 递增 → 未超限 NVIC_SystemReset 重试
    → 超限 rollback_to_other() 切回旧槽
  - **两阶段校验设计：**
    传输层 CRC16 已保证数据完整性
    boot 阶段的 CRC32 是防“元数据错配/半写入”的最终闸门
- **四、新程序启动失败**
  - **boot 保持 COMPLETE + 启动看门狗 + 跳转**
    App 需在窗口内喂狗以及检查活跃槽是否正确
  - 崩溃/卡死 → 不喂狗 → IWDG 复位 → boot_count=2 → 再试
    → 超 3 次 → rollback_to_other() 切回旧槽
  - **正常启动 → 确认 → 结束观察窗口**
    运行期崩溃由 IWDG 复位（不回滚）
- **当前状态：还未真正做过自动回滚**
